# Wuji Glove 踩坑记录

按「现象 → 真实原因 → 判据 → 处理」组织。都是这次实际撞上的，不是推测。

---

## A. 连接与网络

### A1. 一开始把手套当串口设备找

**现象**：`ls /dev/ttyACM* /dev/ttyUSB*` 什么都没有，怀疑 udev 规则、`dialout` 组权限。

**真实原因**：**Wuji Glove 是网络设备**。它通过 USB-C 转以太网转接盒接入，
在系统里表现为一张 `enx<mac>` 网卡，手套自己是网卡另一头的一台 IP 主机（`192.168.1.100/101`），
SDK 走 UDP `50000/50001`。整条链路里没有任何字符设备。

**教训**：拿到新设备先看 `lsusb` + `ip -br link` 的变化，不要预设总线类型。

---

### A2. 右手套 ping 不通，查了半天软件——线其实插反了

**现象**：手套 LED 绿灯正常亮起、呼吸灯正常，但 `192.168.1.101` 不可达，SDK 也扫不到。

**真实原因**：USB-C 线接反了。**Wuji 的线缆两端同一面各有一个白色矩形标识，两端标识必须朝同一面。**
插反时**供电正常（所以灯亮）但数据不通**——这是最有欺骗性的失败模式，因为「灯亮 = 接好了」的直觉在这里是错的。

**判据**：灯亮 + 网络上完全看不见 → 先怀疑线的朝向，而不是 IP/防火墙/SDK。

**处理**：把线两端的白色标识对齐到同一面重插。这次 fix 之后立刻就通了。

---

### A3. 「不可达」的另一种成因：转接盒插到了办公网交换机

**现象**：某张网卡在 `192.168.1.0/24` 上，但目标 IP 不响应，或时通时不通。

**真实原因**：那条网线插到公司交换机上了，网段里全是办公网设备。

**判据（好用）**：**手套是点对点接入，一个网段上正常只有 1 台设备。**
逐网卡扫一遍，扫出 6 台主机 + 一个网关 → 这条线不是手套。

```bash
for n in $(seq 1 254); do ping -c1 -W1 -I <网卡> 192.168.1.$n >/dev/null 2>&1 & done; wait
ip neigh show dev <网卡> | grep lladdr
```

**附带风险**：办公网里可能有设备恰好占用 `.100`/`.101` 并响应 ping，
造成「ping 通但 SDK 扫不到」的假阳性。**拔掉手套后仍能 ping 通 = 冒名设备。**

---

### A4. 多网卡下的 IP 冲突

这台机器有 3 个以太网口。两张网卡同时配在 `192.168.1.0/24` 时
（`enp132s0` 是 192.168.1.165，手套网卡是 192.168.1.10），
两条 /24 路由互相竞争，ping 流量在两张网卡间随机走，表现为**时通时不通**。

**判据**：

```bash
ip route get 192.168.1.100     # dev 是不是接手套的那张
ip neigh show 192.168.1.100    # MAC 是不是手套的
```

**处理**：调 metric 不可靠（另一张网卡的 metric 不归你管）。
**给两个手套 IP 各加一条 /32 主机路由**——最长前缀匹配优先于任何 metric，/32 一定赢：

```bash
sudo nmcli connection modify wuji-glove ipv4.routes "192.168.1.100/32,192.168.1.101/32"
nmcli con up wuji-glove
nmcli -g ipv4.routes connection show wuji-glove
# { ip = 192.168.1.100/32 }; { ip = 192.168.1.101/32 }
```

详见 `bringup.md` §3.3。

---

### A6. 换了转接盒之后，nmcli profile 静默失效

**现象**：`nmcli connection show wuji-glove` 显示一切正常（IP、路由都在），
但网卡上根本没有那个地址，手套不可达。

**真实原因**：nmcli profile 绑的是 `connection.interface-name`，
而 USB 网卡名是 **`enx<MAC>`**。**换一个转接盒 → MAC 变 → 网卡名变 → profile 不再匹配任何设备，
而且不报任何错。**

这次 profile 绑在 `enx6c1ff7c93c06`，换盒后机器上只剩 `enx6c1ff7c93c2d`（还是接公司网的那块），
配置文件看着完全健康，实际一个字节都没生效。

**判据**：

```bash
nmcli -f DEVICE,TYPE,STATE,CONNECTION device status          # 手套网卡的 CONNECTION 列是不是 wuji-glove
nmcli -g connection.interface-name connection show wuji-glove # 对比现存网卡名
ip -br addr show <现存网卡>                                   # 地址到底配上没有
```

**处理**：

```bash
sudo nmcli connection modify wuji-glove connection.interface-name <新网卡名>
nmcli con up wuji-glove
```

**教训**：**「配置文件是对的」不等于「配置生效了」。** 看 profile 没用，
要看 `ip -br addr` 和 `ip route get` 的实际状态。

---

### A5. 刚插拔过，但内核一个事件都没有

```bash
journalctl -k --since "-10 min" | grep -iE "usb [0-9]|ax88|renamed"
```

**零输出 = 这次插拔根本没被系统感知。** 别再往软件方向查了，回去查线和接口。
正常插入必然有 `usb 4-1: Product: USB3.1 Hub` / `AX88179B` / `renamed from eth0` 这几行。

（反过来也成立：本次会话末尾突然扫不到手套，`lsusb` 里两个 ASIX 只剩一个、
`enx6c1ff7c93c06` 整个消失 —— 就是转接盒被物理拔掉了，跟代码无关。）

## B. SDK / 进程行为

### B1. pkill 杀可视化 → 下一次启动画面冻结

**现象**：用 `pkill -f dual_glove_viz` 杀掉进程后重新启动，新进程的 HUD 帧数在涨、
状态栏在刷，**但 3D 画面冻结在某一帧不动**。

**真实原因**：粗暴 kill 没有 `close()` 掉订阅，**设备侧留下了孤儿 session**。
新进程的订阅被旧 session 的超时逻辑一并带掉——数据流断了，但渲染循环还活着，
所以「HUD 在动、画面不动」。

**处理**：
- 正常退出走 `Ctrl-C` / 让脚本自己 `close()` 每个 subscription。
- 已经杀过了：等设备端 session 超时回收，或断电重插手套。
- 排查时先确认 **没有别的客户端（Wuji Studio、另一个脚本）占着设备**。

---

### B2. 在 SIGTERM handler 里 `raise KeyboardInterrupt` —— 反而杀不掉进程

**踩法**：为了让 `--secs` 到点后干净退出，注册了

```python
signal.signal(signal.SIGTERM, lambda *_: (_ for _ in ()).throw(KeyboardInterrupt))
```

**结果**：进程对 SIGTERM 完全无反应，只能 `-9`。

**原因**：异常在 signal handler 里抛出，但主线程正阻塞在 **GUI 事件循环（C 层）** 里，
异常传不出 C 栈，等于**注册了一个吞掉 SIGTERM 的 handler**——比不注册还糟。

**正确做法**：handler 里只置一个 flag / 调用 GUI 框架自己的退出 API
（如 `plt.close('all')`、`timer` 回调里检查 deadline），让退出发生在 Python 层。

---

### B3. 固件 ELF 下载 404

日志里会出现固件符号表 / ELF 下载失败的 404。**无害**，只影响设备日志的符号解码，
不影响数据通路。不用管。

---

### B4. `calibrate()` 标的不是 EMF

`calibrate()` 标定的是**你的手的几何尺寸**，产物是 URDF（骨长），用于 IK 解算。
**它不是 EMF 幅度标定，修不了「某个 EMF 通道没数据」的问题。** 别指望重新标定能救回死掉的手指。

### B5. 标定产物在默认 SDK 用户下不生效

产物路径：`~/.wuji/sdk/users/<user_id>/models/{left,right}_hand.urdf`。

**默认用户会跳过标定产物，永远加载内置默认 URDF。**
必须先 `create_user` / `switch_user` 到具名用户，标定才写得进去也读得出来。
同一用户下同侧手套共享模型，换一只同侧手套不用重标。

## C. 数据判读（最容易误判的部分）

### C1. 「死掉的手指」照样会被画出来

**这是本次最重要的教训。**

一根 EMF 通道完全无输出时，解算器**不会报错、不会留空**，而是输出一个
**固定的默认姿态**。可视化把它正常画出来，看起来只是「这根手指不太灵活」，
极易被归因为「没戴好」「环境干扰」。

**必须看 `confidence` 和逐通道数据，不能只看画面。**
本次右手中指就是这么被漏掉又找回来的。

### C2. `confidence = 0` 和 `confidence` 低是两回事

| 值 | 含义 |
|---|---|
| >0.9 | 可信 |
| 0.8~0.9 | 偏低 |
| <0.8 | 环境干扰严重（官方定义） |
| **恒为 0.0000** | **无数据 —— 不是「低」，是「没有」** |

不要把恒零并进「置信度低」一类去处理，两者排障方向完全不同。

### C3. `--save` 出来的 4 帧一模一样，不是代码 bug

**先看脚本打印的 `max disp`。** 1.6mm 这种量级就是手套摊在桌上没动。
戴上手套动一动再截。

### C4. 桌面上摊着测出的 confidence 没有参考价值

实测两只手套摊在桌上、紧挨主机和显示器时，各指 confidence 只有 **0.49~0.72**，
全部低于官方 0.8 干扰线。这不说明手套坏了。
EMF 需要：手距发射线圈 30cm 内、远离金属和电子设备。

### C5. 非拇指手指的第 5 个角度槽恒为 0，是占位不是故障

`hand_joint_angles` 里每指 5 个槽位，**非拇指手指只有前 4 个有效**，第 5 个恒为 0。
写检查脚本时要按手指区分，否则会误报。
（`glove_healthcheck.py` 里已按 `valid = rng if nm == "thumb" else rng[:4]` 处理。）

## D. 本次实例：右手中指 EMF 无输出 → **断电重插后自行恢复**

### ⚠️ 结论已修正：这不是永久故障，不要照抄「返厂」结论

**最初的观测（多次采样，有左手对照，数据本身没错）**：

1. `emf_poses` **ch2（middle）位置向量模长恒为 `0.00000`**，其余 4 通道 0.079~0.131 正常。
2. 中指各指节 `confidence` **恒为 `0.0000`**，其余手指 0.49~0.73（虽低但非零）。
3. 骨长几何正常（90.5 / 42.0 / 31.7 / 29.9 mm），排除模型/标定问题。
4. 同一台机器上的**左手套 5 个通道全部正常**（0.074~0.137），构成对照——
   排除环境、驱动、网络、SDK 版本等共因。

按当时的证据，这是一条教科书式的「接收线圈无输出」证据链，我据此写了返厂建议。

**后来发生了什么**：转接盒被物理拔掉过一次，重新接上、手套重新上电之后复测：

| | 故障时 | 断电重插后 |
|---|---|---|
| `emf_poses` ch2 模长 | **0.00000** | **0.13253** |
| middle `confidence` | **0.0000** | **0.6618** |
| `glove_healthcheck.py` | 退出码 1 | **退出码 0，未发现硬件故障** |

**真实性质：上电初始化失败导致的间歇性故障，不是线圈物理损坏。**

**教训（比故障本身更重要）**：

> **`corrected amplitude = 0` 证明的是「这次上电后这条通道没工作」，
> 不是「这条通道坏了」。报障前必须断电重插、重新上电，再复测一次。**

否则会把一个重启就好的问题当成永久硬件故障报上去。软件层面无法区分
「出厂标定数据缺失」「线圈物理损坏」「本次上电初始化失败」——三者都归零。

### 判据可靠性：只有 [1][2] 能用

早期我把「中指关节位移逐位恒为 0」也写成了证据之一。**这条不可靠，实测已推翻。**

同一只手套、同样的死通道，两次采样表现完全相反：

| 采样 | 中指关节位移 | 静止时角度摆幅 |
|---|---|---|
| 第一次 | 0.000 / 53.8 / 99.2 / **140.6 mm**（大幅乱摆） | **99.5°** |
| 第二次 | 接近 0（几乎不动） | 7.2° |

一根通道死掉后，解算器**既可能冻结在默认姿态，也可能输出完全不受约束的垃圾**，
取决于当时的解算器状态。

**可靠判据只有两条：`emf_poses` 该通道模长恒为 0，以及该指 `confidence` 恒为 0。**
`glove_healthcheck.py` 的 [4][5] 两项保留作参考，但结论不建立在它们之上。

### D2. 右手 ring **触觉**分区无输出（这个还在，未恢复）

跟上面的中指 EMF 是**两码事**：那是动捕通道，这是触觉传感器。

**证据**（`tactile_zones`，603 帧 / 5s，取各区剔除无效点后的统计）：

| 分区 | 右手 max | 左手 max（对照） |
|---|---|---|
| thumb | 0.403 | 0.261 |
| index | 0.176 | 0.138 |
| middle | 0.179 | 0.126 |
| **ring** | **0.005** | **0.895** |
| pinky | 0.235 | 0.266 |
| palm | 0.706 | 1.000 |

右手 ring 的 p50 = 0.000、p99 = 0.004，整段采样恒在噪声底；
**同一只手套的其余 5 个分区都正常，左手同名分区正常** —— 双重对照，排除共因。

**判据不能写成 `== 0`**：坏掉的分区不是精确输出 0，而是 0.005 这种噪声底。
`dual_glove_viz.py` 里用的是 `DEAD_MAX = 0.02`（好的分区静息就有 0.13+，量级差 20 倍以上，阈值很宽松）。

**复现**：

```bash
python scripts/dual_glove_viz.py --save out.png --secs 5
# -> 右手行打印 NO TACTILE: ring，柱状图该区标红 DEAD
```

**按 D 的教训，报障前先断电重插复测一次。** 仍不恢复再带上表联系 support@wuji.tech。

**报障模板**：

```

前置: 已断电重插 + 重新上电复测，故障仍复现（不做这步别报）

  1) <主判据：emf_poses chN 模长恒 0 / 该触觉分区 max 恒在噪声底>
  2) 同手对照：其余通道/分区数值正常（列出来）
  3) 同机对照：另一只手套对应通道/分区正常，排除环境/驱动/SDK 共因
  4) 骨长几何正常，已排除标定/模型问题
复现: python glove_healthcheck.py --sn <SN> --secs 6
```

### C6. 三个触觉 topic 订阅成功但永远不发帧

`tactile_binary` / `tactile_residual` / `tactile_point_cloud` 这三个 topic **存在、订阅不报错、
但默认一帧都不发**（需要先做触觉标定）。

这个失败模式很坏：`subscribe_with_callback()` 只在「订阅本身失败」时抛异常，
**「订阅成功但对方永不发数据」不会抛任何东西**。用 try/except 包起来照样静默通过，
面板永远空着，看起来像渲染代码写错了。

**实测能用的只有两个**：

| topic | 内容 | 状态 |
|---|---|---|
| `tactile` | 768 个原始触点 | 可用，~120Hz |
| `tactile_zones` | 6 个分区（thumb/index/middle/ring/pinky/palm） | 可用，~120Hz |
| `tactile_binary` | — | **0 帧** |
| `tactile_residual` | — | **0 帧** |
| `tactile_point_cloud` | — | **0 帧** |

**判据**：给回调加个计数器，跑 3 秒看 `n == 0`。别信 docstring，实测。

### C7. 触觉必须扣静息基线，否则一直显示「在被按」

手套摊在桌上完全没受力时，各分区读数 **p95 已达 ~0.2、峰值能到 1.00**
（自重、桌面反作用力、零点漂移）。直接把 0~1 映射成颜色，画出来永远是「满手都在受力」。

`dual_glove_viz.py` 的做法：启动先采 2s 静息，取各区 **p99** 作基线（不用 max，
避免个别尖峰把基线抬太高），之后只显示高于基线的部分。
所以**启动那 2 秒内别碰手套**，否则基线被抬高，之后轻按就没反应了。
基线时长可调：`--baseline-secs 3`。

### C8. 768 个原始触点里 219 个恒为 `-1`

`-1.0` 是**无效触点标记**，不是「压力为 -1」。统计前必须先 `v[v != -1.0]` 剔掉，
否则均值/最小值全被带偏。各区有效点数实测：
thumb 52 / index 52 / middle 58 / ring 52 / pinky 45 / palm 290。

另外：**768 个触点的二维物理排布没有公开的 ground truth。**
不要把它 reshape 成 24×32 画成热图——那会让人从图里读出并不存在的空间信息
（而且 24×31=744 ≠ 768，早期代码就是这么错的）。

## E. 环境相关（这台机器）

- **robot 机器没有免密 sudo。** 需要 root 的排查命令（部分 `journalctl`、`ufw status`）
  要么走交互式 sudo，要么改用无需权限的替代（`/sys/class/net/*` 直接读）。
  `check_gloves.sh` 里的 ufw 检查用 `sudo -n` 并在失败时降级提示，就是为此。
- **Wuji 文档站从开发机访问不到，需要在 robot 机器上 curl。** 查官方文档时注意在哪台机器上执行。
- **`xwd` 截图的 stride 不等于 `bpp/8`。** 必须用头里的 `bytes_per_line // width` 算，
  否则解出来的图是斜的。踩过一次。
