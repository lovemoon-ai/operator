# 实机经验与证据等级

记录日期：2026-09-07/08。这是调试经验，不是下一次机器的即时状态。

## 证据等级

- **本机实测**：实际收到数据/回执，并通过对应物理反馈验证。
- **用户确认**：现场控制来源、设备使用限制；保留最新纠正。
- **官方代码/手册**：证明接口设计和示例，不证明本机固件已支持或已动作验证。
- **推断/未解**：必须标注，不升级为既定根因。

## 经过与结论

1. 本项目限制全部操作在 Conductor 远程 Ubuntu。曾因 CLI 更新将 remote-exec 改为 remote exec。机器人系统缺 rg，用 grep/find。
2. 修复头部图像链路：缺腕相机导致 teleimager 重启；备份配置后只禁用缺失腕相机流。头部收到实际双目JPEG，夜间图像很暗、白天图像清晰。该修复与底盘深度相机无关。
3. 初始前进尝试：Unitree API返回0，但底盘实际不动。最终查到真实 system emergency stop；REST/驱动日志比表面回执更有解释力。曾问软件关机并执行成功，重启后重新读状态。
4. 重启后的 motor brake released 需要用户现场复位。软件无法物理拨开关，清报警也不等于解除硬件条件。
5. 30厘米任务多段完成：
   - 初段约6.8厘米因实测速度超过0.08m/s保护停止。
   - 低速续段到约28.9厘米，进一步降速输入0.008不产生运动，deadline结束并停止。
   - 小段微调补足，累计约30.5厘米，独立反馈确认停稳；发送原始移动前/后照片。
   - 30厘米名义值不是精确30.000厘米；每段都必须保留同一起点。
6. 后续新1米任务：
   - 第一次启动检测到已在运动，未发前进指令。
   - 确认静止后重新尝试，约33厘米处出现 unexpected_motion 保护，最终确认零速度，未完成1米。
   - 用户随后确认自己当时操作过机器人。不能将这次偏航直接定为机器人机械故障，也不能假定未来不会有控制冲突。
7. 深度报警诊断：
   - health返回0x01040A00，布尔hasDepthCameraDisconnected却false；必须保留完整baseError。
   - enable=true及软重启未消除反复报警。
   - 官方默认admin/admin111登录成功；诊断流有激光和基础传感器、没有深度消息。
   - **随后用户明确：底盘深度相机仅内置导航使用、不支持用户连接。** 因而之前“没有用户侧深度帧→相机损坏”的推断撤回；未确定哪颗相机异常，也未确认根因或修复。
8. 上半身：阅读了G1-D专用C++关节与升降示例，确认映射/消息设计；没有实机动作验证。

## 下个AI不应重复

- 旧照片、旧health、旧定位不冒充当前数据。
- 输入速度×等待时间不当实际移动距离；测量反馈闭环验收。
- 不把历史阈值当厂家限值，不为了走完目标盲目放宽保护。
- 不从续走位置再执行完整原距离。
- 不把操作者同时控制引起的运动自动认定为驱动故障。
- 不把深度用户接口的产品限制“修复”为可访问，也不伪造数据消警。
- 不把通用示例支持RealSense等同于本机安装该相机。
- 不把无/dev/video节点当UVC断开；libusb可能直接占用。
- 不用别的G1示例控制G1-D的无效腿关节/腰roll。
- 不把HeightAdjust的归一化速度当目标高度。
- 不因解释/编写skill就触发示例动作。
- 不编造已修复、已完成、哪个相机损坏、或者本机上肢实测成功。
